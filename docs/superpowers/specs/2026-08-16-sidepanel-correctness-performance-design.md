# 侧栏正确性与性能优化设计

日期：2026-08-16

## 目标

在不改变现有用户功能、不新增 Chrome 权限、轮询或后台常驻任务的前提下，解决侧栏标签事件的状态竞态、内存生命周期问题和 500 标签下的主要渲染热点。分组块右键菜单的“关闭分组”必须始终以最新成员集合为准。

本次不引入列表窗口化。窗口化作为后续容量项目单独设计和验收，避免与事件正确性修复互相干扰。

## 已确认问题

1. `tabs.onUpdated` 延迟到微任务后，`removed`、`moved`、`activated` 或 `replaced` 可以先同步处理；旧的更新快照随后 flush，会把已删除标签重新加入 Store，或覆盖索引、活动状态和替换关系。
2. 同一微任务中的多个不同标签更新仍逐项执行 favicon 同步和渲染判断，不能真正合并为一个 UI 批次。
3. `TabStore.activate()` 仍遍历并复制全部标签；`snapshot()` 后的列表模型和树模型仍重复排序。
4. `snapshot()` 返回内部 `TabViewModel` 对象引用，消费者可以修改 Store 与排序缓存。
5. 替换 ID 映射与分组移动完成计数存在延迟清理；树会话存储串行保留所有中间快照。
6. 树的可见节点展开仍使用递归，异常深链可能耗尽调用栈。
7. 关闭分组从 Store 读取成员；成员归属尚在延迟更新队列时，可能遗漏刚加入分组的标签。

## 方案

### 1. 带版本屏障的标签更新批次

新增一个只负责批处理 `onUpdated` 的调度器。每个标签 ID 维护递增的版本号，`schedule(tab)` 保存 `{ tab, version }`；flush 只应用版本仍与当前版本一致的记录。

所有会改变标签身份、顺序或活动状态的同步事件都调用 `invalidate(tabId)`：

- `removed`、`detached`：删除待更新并推进版本。
- `moved`、`activated`：推进目标标签版本，阻止旧索引或旧 active 快照覆盖当前状态。
- `replaced`：同时使旧 ID 和新 ID 的待更新失效。

调度器的 flush 回调改为同步，只接收有效的最新快照。这样不会产生被忽略的异步 rejection；若未来确需异步回调，必须在调度器内显式捕获并转为受控错误状态。

### 2. 单批状态应用与渲染决策

flush 不再对每个标签调用独立的 `applyEvent`。它先顺序更新 Store 并收集变更：

- 结构变更：标签不存在、索引、分组或固定状态改变，需要一次 `renderTabList()`。
- 行属性变更：标题、URL、favicon 等，仅对对应行调用 `patchTab()`。

一批更新最多调用一次 `syncShortcutFavicons()`；如果存在结构变更，最多完整渲染一次。同步生命周期事件继续即时处理，但先使该标签的延迟更新失效。

### 3. Store 快照与活动标签

`TabStore` 保留内部的有序缓存。供渲染使用的快照类型改为 `readonly Readonly<TabViewModel>[]`，并在边界上返回冻结或独立的不可写值，不能泄露 Map 中的可变对象。

`activate(id)` 只读取当前活动标签 ID，分别写入旧活动标签和新活动标签；当 ID 未变化时不写入。Store 维护活动 ID 以避免全量扫描。各写操作统一失效有序缓存。

`list()` 保持返回可修改副本的既有公共语义；所有内部只读消费者改用安全快照。

### 4. 单一排序来源

`TabStore.snapshot()` 是唯一的 pinned + Chrome index 排序来源。`buildTabListItems` 和 `buildTabForest` 接收该有序输入后不再复制排序，只在需要分区时线性遍历。

不得用“调用方恰好传入已排序数组”作为隐式契约：函数参数或命名必须明确为已排序快照，测试须验证输入顺序不被重新排序。

### 5. 生命周期与会话写入

- 树会话迁移完成后，收集并删除本次使用的全部 replacement key；没有树关系的 replacement 在本次迁移结束后也必须清除。
- `groupMovesCompletedByEvent` 消费到零时删除键，不保留零计数。
- 树会话存储变为“一个进行中的写入 + 一份最新待写状态”。后续保存覆盖待写状态，不为每个中间状态创建 Promise 链；完成当前写入后只持久化最后一个状态。

### 6. 迭代树遍历

将可见森林展开和活动祖先查找改为显式栈。保持现有深度、顺序、折叠与活动祖先标记语义，禁止改变标签树边界规则。

### 7. 关闭分组的最新成员语义

执行 close 命令前先使目标分组所有待更新立即 flush，然后从 Store 获取成员 ID 并执行一次 `chrome.tabs.remove(ids)`。若同步 flush 后成员为空，则不调用 Chrome API。

该路径继续复用 `executeGroupCommand` 的 busy 门禁、错误消息和一次重同步；不新增确认对话框。

## 验收与测试

必须新增以下回归测试：

1. `updated -> removed`、`updated -> moved`、`updated -> activated`、`updated -> replaced` 后 flush，验证旧状态不回写。
2. 多标签 updated 同批处理时，验证 favicon 同步不超过一次、结构渲染不超过一次、非结构更新仅 patch 对应行。
3. 修改 snapshot 的数组或元素不会影响后续 `get()`、`list()` 与渲染顺序。
4. 活动标签切换只修改旧、新两个标签；同一标签重复激活无写入。
5. Store 已排序快照经平面列表和内容树构建后不产生第二次排序。
6. replacement key、分组移动计数和连续树会话写入均在操作结束后不保留过期状态。
7. 深链标签树的展开与活动祖先查找不使用递归，并保持既有输出。
8. 成员 groupId 更新尚未自然 flush 时执行关闭分组，`tabs.remove` 仍收到该分组全部最新成员。

性能验收使用既有 `benchmark:tabs`，记录 100 和 500 标签下的中位数、P95 与 DOM 节点数。当前基线为 500 标签中位数约 60ms、P95 约 101ms、4500 DOM 节点；本次目标是明显降低中位数与 P95，并保持 DOM 节点数不增加。若仍无法达到交互帧预算，进入独立的窗口化渲染项目。

所有实现完成后须通过：`npm run typecheck`、`npm test -- --run`、`npm run build`、`node scripts/check-dist.mjs`，并在已加载扩展的 Chrome 中完成“关闭分组”实机验收。

## 非目标

- 不新增权限、网络请求、轮询、后台服务或长期缓存。
- 不改变现有标签树、分组拖拽、快捷网站或智能分组的用户语义。
- 不在本次引入列表窗口化、虚拟滚动或新的 UI 控件。

## 最终基准

2026-08-16 在当前实现运行 `npm run benchmark:tabs`：100 标签中位 8.558ms、P95 11.585ms、900 个 DOM 节点；500 标签中位 43.674ms、P95 67.56ms、4500 个 DOM 节点。500 标签的中位与 P95 均低于设计基线 60ms 和 101ms，未进入窗口化渲染范围。
